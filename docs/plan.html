1.1 Toolchain khi không có quyền admin

Đã kiểm: phiên không có quyền admin, chưa có Visual Studio / Build Tools, chưa có Rust. Đêm nay không ai bấm UAC. Bước đầu tiên của M0, theo thứ tự, dừng ở đường đầu tiên chạy được:

  1. Kiểm lại quyền admin và vswhere / thư mục Visual Studio (phòng khi có bản cài ở chỗ khác).
  2. Cài rustup theo user (winget install Rustlang.Rustup --scope user, hoặc rustup-init.exe tải từ static.rust-lang.org, không cần admin), toolchain 1.99.1.
  3. Thử cài Build Tools theo cách không nâng quyền (winget ... --scope user). Gần như chắc sẽ cần UAC; nếu installer hiện UAC hoặc trả lỗi quyền thì bỏ qua, không thử lặp.
  4. Đường thay thế thứ nhất, target MSVC không cần Visual Studio: cargo-xwin (dùng lld-link và clang-cl của LLVM bản zip, tải CRT và Windows SDK của Microsoft về thư mục user; xwin yêu cầu chấp nhận giấy phép của Microsoft cho các gói này, ghi vào DECISIONS.md). Tauri, windows crate và WebView2 đều chạy trên target x86_64-pc-windows-msvc này.
  5. Đường thay thế thứ hai: target x86_64-pc-windows-gnullvm với llvm-mingw bản zip (không cần admin). Tauri không chính thức hỗ trợ target GNU trên Windows; chỉ dùng nếu đường 4 hỏng, và chạy đủ E2E trên bản build đó.
  6. Kiểm linker ngay bằng một crate "hello" và một app Tauri trống trước khi viết code khác. Nếu cả 4 và 5 đều hỏng: ghi chặn vào STATUS.md, báo reviewer, và vẫn viết + kiểm tra những phần không cần link (frontend, cargo check các crate Rust thuần nếu được).

NSIS do Tauri bundler tự tải vào thư mục cache của user; msedgedriver là file zip, không cần admin.

3. Mô hình dữ liệu

3.1 Ô (slot)

Ô 4 byte [b0, b1, b2, b3], loại = b0 & 0x0f (bảng nhảy firmware 0x76a0).

pub enum SlotKind {
    Empty,                                   // loại 0 và 8-15 (firmware coi như ô trống)
    Mouse(MouseAction),                      // loại 1
    Key { mods: ModMask, usage: u8 },        // loại 2: b1 = mặt nạ modifier (bit i -> 0xe0+i), b2 = mã HID
    Consumer(u16),                           // loại 3: media
    System(u8),                              // loại 4: ngủ, tắt máy, thức
    Macro { raw: [u8; 3] },                  // loại 6: chỉ hiển thị trong bản đầu
    Reserved { kind: u8, raw: [u8; 3] },     // loại 5, 7: chưa phân tích, chỉ hiển thị
    Extension { kind: u8, raw: [u8; 3] },    // loại 8-15: chừa cho bộ máy kiểu QMK (FAQ câu 9)
}
pub struct Slot { bytes: [u8; 4] }           // luôn giữ nguyên 4 byte gốc
  • Slot luôn lưu đủ 4 byte; SlotKind là cách nhìn. Giải mã rồi mã hóa lại cho đúng 4 byte cũ với mọi giá trị (kể cả nibble cao của b0, b3 khác 0, mã HID lạ như 0xa4 Fn). Test vét cạn cho mọi tổ hợp b0 và property test cho phần còn lại.
  • Sửa một ô chỉ sinh byte qua encode(SlotKind) có kiểm giới hạn; ô "Empty" luôn mã hóa thành 00 00 00 00.
  • Mã hóa loại 1, 3, 4 lấy theo firmware và FILCO Assist (mục 3.2). Loại 6 (macro, lệnh 0x15), 5, 7 và 8-15 đọc được, hiển thị nguyên byte, không sửa trong bản đầu; kiến trúc đã có chỗ: thêm biến thể SlotKind, thêm tab trong UI, thêm khả năng slot_types trong mô tả model.

3.3 Trang và layer

  • Page([u8; 512]), offset ô của chỉ số k do model quy định; với giao thức costar-v1 là 0x40*(k&7) + 4*(k>>3). Mọi truy cập ô đi qua SlotAddressing của model, không có công thức ghi cứng ở chỗ khác.
  • LayerSet = N trang (M10SP: 4). Diff giữa hai LayerSet cho danh sách (layer, chỉ số, ô cũ, ô mới), kể cả ô của vị trí ma trận không có phím vật lý (ví dụ file nhập vào có byte lạ ở chỉ số 53): UI liệt kê riêng các ô này.

Bảng PID này nằm trong dữ liệu (models/known-devices.json) để UI gọi đúng tên thiết bị chưa có bố cục, không nằm trong code.

  • Bố cục M10SP dựng từ ROWS trong gen_layers.py (hình học) cộng bảng chỉ số ma trận đọc từ keymap mặc định của ảnh V72 (tên do mình viết, không chép dữ liệu nhị phân). Vị trí đã kiểm trên máy thật: 27 P, 70 M10, 73 Fn, 76 Space phải, 77 Space trái, 83 Alt trái. Chưa chắc: Alt phải là 78 hay 87 (keymap có cả hai, một chỉ số là của bản JP); mục 11.

3.5 File sao lưu và file xuất

  • Sao lưu: đúng định dạng fnmap.py (thư mục layer{N}.bin + manifest.json có SHA-256 từng layer), thêm khóa app (phiên bản ứng dụng, id model, lý do sao lưu). fnmap.py restore đọc được bản sao lưu của ứng dụng và ngược lại; có test cả hai chiều. Lưu ở %LOCALAPPDATA%\FilcoConfigurator\backups\<model>\<thời gian>\, ghi file tạm rồi đổi tên, fsync trước khi cho phép ghi thiết bị.
  • Xuất/nhập: một file .filco-layers.json (định dạng văn bản, dễ chia sẻ): format_version, id model, PID, thời gian, mỗi layer là hex 512 byte kèm SHA-256, cộng danh sách ô đã giải mã để người đọc hiểu (chỉ để đọc; khi nhập chỉ dùng hex). Nhập cũng nhận thư mục sao lưu kiểu fnmap.py. Nhập chỉ nạp vào bản đang sửa, không ghi thiết bị; ghi vẫn qua diff và xác nhận.

4. Giao thức HID trên Windows

4.1 Tìm và mở interface (đúng như fnmap.py)

  1. HidD_GetHidGuid, SetupDiGetClassDevsW(DIGCF_PRESENT | DIGCF_DEVICEINTERFACE), duyệt SetupDiEnumDeviceInterfaces + SetupDiGetDeviceInterfaceDetailW.
  2. Mỗi đường dẫn: CreateFileW(path, 0, FILE_SHARE_READ | FILE_SHARE_WRITE, NULL, OPEN_EXISTING, 0, NULL). Quyền truy cập 0 là bắt buộc: collection bàn phím bị Windows giữ độc quyền đọc/ghi, nhưng feature report vẫn đi được với handle quyền 0 (cách FILCO Assist và fnmap.py làm).
  3. HidD_GetAttributes (VID, PID, VersionNumber = REV firmware, ví dụ 0x0072) và HidD_GetPreparsedData + HidP_GetCaps. Khớp khi VID và PID có trong một model, UsagePage == 1, InputReportByteLength == 9, OutputReportByteLength == 2, FeatureReportByteLength == 65. Trên M10SP đó là interface MI_00. Thiết bị có VID FILCO và caps khớp nhưng PID lạ: hiện "model chưa hỗ trợ", chỉ cho xem thông tin.
  4. Hơn một interface khớp: không tự chọn; UI cho chọn thiết bị (fnmap.py thì từ chối).
  5. Cắm/rút: CM_Register_Notification với GUID_DEVINTERFACE_HID, lọc theo đường dẫn; thay cho message window.

Vì sao không dùng crate hidapi: nó không trả độ dài report trong caps nên không lọc được như FILCO Assist, và đường mở thiết bị thử quyền đọc/ghi trước. Crate windows cho gọi đúng từng API như fnmap.py, không kéo thêm C.

4.2 Gói và phiên (đối chiếu fnmap.py từng byte)

BướcGói gửi (65 byte, byte 0 = report ID 0)Kiểm phản hồi
Lệnh[1]=0x04, [2]=cmd, [9]=len, [0xb]=layer (với 0x10/0x11)GetFeature: [1]==4, [2]==cmd, [4]==1, [9]==len
Đọc trang (0x10, len 8)sau ACK: 8 lần GetFeature, dữ liệu là byte 1..64checksum += tổng cả 65 byte mỗi gói
Ghi trang (0x11, len 8)sau ACK: 8 lần SetFeature [0] + 64 bytechecksum += tổng 65 byte mỗi gói
Kết thúc (0x02, len 0)gói lệnh thườngchecksum thiết bị ở [5..9] little-endian phải bằng checksum máy
  • Mỗi SetFeature/GetFeature có khoảng chờ cấu hình được theo model (delay_ms, mặc định 100 ms như FILCO Assist).
  • Ghi trang xong: chờ, đọc lại bằng 0x10 + 0x02 và so 512 byte.
  • Lỗi được phân loại: Disconnected, NoAck { cmd, got }, ChecksumMismatch { device, host }, ReadbackMismatch { layer, first_diff }, Io(win32 error). Không tự thử lại lệnh ghi; lệnh đọc thử lại tối đa 2 lần.
  • Lệnh 0x05/0x06 (basic info), 0x12-0x17 (macro, Game Mode) không có trong bản đầu. Riêng 0x06 ghi đè cả khối basic info, gồm cờ reset về mặc định ở byte 0x10 (FILCO Assist dùng nó để tắt ghi macro phần cứng và để reset), nên ứng dụng không bao giờ gửi 0x06. Giai đoạn sau có thể dùng 0x05 (chỉ đọc) để hiện layer đang dùng (byte 0x00). Enum lệnh trong filco-protocol chỉ có 0x02, 0x10, 0x11; thêm lệnh mới phải thêm có chủ đích.

4.3 Luồng I/O

Mọi I/O thiết bị chạy trên một luồng worker riêng (một handle, các lệnh xếp hàng), không bao giờ trên luồng UI. Tiến độ (gói thứ mấy, layer nào) gửi lên UI qua event. Hủy chỉ được giữa hai layer, không giữa các gói của một layer.

4.4 FILCO Assist

  • Phát hiện FilcoAssistUI.exe và FilcoAssistTray.exe qua CreateToolhelp32Snapshot. Đang chạy thì hiện cảnh báo thường trực, nút Lưu bị tắt kèm giải thích; kiểm lại ngay trước khi gửi gói ghi đầu tiên.
  • Đọc (chỉ đọc) %APPDATA%\FILCO\filco_assist_config.json: layer nào gắn profile thì cảnh báo "FILCO Assist có thể ghi đè layer này khi lưu profile". Không sửa file này trong bản đầu (giai đoạn sau: tùy chọn đồng bộ AssignedKeys như repo phân tích từng làm tay).

4.5 Ràng buộc đêm nay với thiết bị thật

  • Được phép trên thiết bị thật: liệt kê và mở interface (quyền 0, attributes, caps) và phiên đọc đầy đủ y như fnmap.py show/backup: 0x10 + 8 GetFeature + 0x02 (0x02 trong phiên đọc chỉ trả checksum, không ghi flash; đường này đã chạy nhiều lần trên chính bàn phím này). Trước mỗi lần chạy kiểm FILCO Assist đã đóng.
  • Cấm trên thiết bị thật đêm nay: 0x11, 0x15, 0x16, 0x17, 0x06 và mọi lệnh khác ngoài 0x10/0x02. Phiên ghi (0x11 ... 0x02) chỉ chạy trên thiết bị giả.
  • Chặn bằng code, không chỉ bằng kỷ luật: filco-hid-windows có WritePolicy. Chế độ ReadOnly từ chối trước khi gọi HidD_SetFeature mọi gói không phải gói lệnh 0x10 hay 0x02 (kể cả gói dữ liệu); có unit test cho chặn này. filco-cli và mọi test chạm thiết bị thật đêm nay chỉ tạo transport ở ReadOnly. Ứng dụng chỉ chuyển sang ReadWrite trong SafeWriter, ngay sau khi người dùng bấm xác nhận; đêm nay không bấm Lưu với thiết bị thật.
  • Test tích hợp: đọc 4 layer, so SHA-256 với bản cấu hình hiện tại (firmware/configs/2026-10-31_Layer4Snip, khớp bản đọc lại backups/20261031-165259). Không khớp thì không phải lỗi của ứng dụng chừng nào checksum 0x02 đúng (người dùng có thể đã đổi layer); khi đó so với bản fnmap.py backup mới nhất thay vì tạo bản mới bằng fnmap.py.
  • Đo khoảng chờ đọc nhỏ hơn 100 ms: các mức 50, 25, 15, 10 ms, mỗi mức tối đa 10 phiên đọc 4 layer, tổng không quá 50 phiên đọc trang trên máy thật. Gặp checksum sai, NoAck hay dữ liệu khác bản 100 ms ở một mức thì dừng ngay, không thử mức nhỏ hơn. Bản phát hành chỉ dùng mức nhỏ hơn 100 ms nếu mức đó qua toàn bộ phép đo, và lấy mức lớn hơn kế tiếp làm biên an toàn; khoảng chờ ghi giữ 100 ms. Kết quả ghi vào STATUS.md.
  • Ứng dụng phát hành dùng phiên đọc đầy đủ có 0x02 như FILCO Assist.

6.2 Golden bytes từ fnmap.py

tools/golden/gen_fnmap_golden.py nạp fnmap.py từ đường dẫn trong biến môi trường FILCO_FNMAP (không chép vào repo), thay hid.HidD_SetFeature/HidD_GetFeature bằng thiết bị giả bằng Python (trả ACK, trả trang fixture, tính checksum như firmware) và time.sleep bằng hàm rỗng, rồi chạy Keyboard.read_page và Keyboard.write_page trên các trang thật. Kết quả là file JSON liệt kê từng gói theo thứ tự (chiều, 65 byte hex), commit vào tests/fixtures/golden/. Test Rust chạy cùng kịch bản trên filco-sim có ghi transcript và so khớp từng byte. Như vậy Rust được đối chiếu với chính code đã chạy đúng trên thiết bị thật, không qua bản dịch tay.

6.3 Thiết bị giả filco-sim

Mô hình hành vi theo fnmap.py, FN_ANALYSIS.md mục 2 và FAQ câu 6: bộ nhớ "flash" 4 trang, phiên lệnh (chờ ACK, đếm gói, cộng checksum), 0x02 so checksum rồi mới "ghi flash" với phiên ghi, đọc trả nội dung flash. Tiêm lỗi theo kịch bản khai báo: fail_at(phase, packet, kind), với kind = rút cáp, ACK sai, checksum sai, đọc lại lệch, im lặng. Có bộ đếm để test khẳng định số gói và thứ tự gói.

Hạn chế: đây là mô hình suy từ phân tích, không phải code firmware. Mốc M7 thử thay bằng firmware thật.

6.4 Giả lập firmware thật (mốc M7, có giới hạn thời gian)

Khả thi một phần. emu.py hiện chạy vòng lặp chính, quét ma trận và bộ điều phối phím, nhưng không mô phỏng USB và không mô phỏng ghi flash (IAP). Cách làm:

  1. Tìm trong ảnh V72 trình xử lý lệnh feature (V60 là 0x9fde, 0xa282, 0xa30e; V72 phải dò lại) và bộ đệm gói mà ngắt USB điền vào.
  2. Trong tools/fwsim/ (Python, Unicorn, code mới viết, nhận đường dẫn ảnh firmware của người dùng qua biến môi trường, không chép ảnh vào repo): đặt 64 byte gói vào bộ đệm, gọi thẳng trình xử lý, đọc gói trả lời; móc thanh ghi flash để ghi vào flash giả.
  3. Cầu nối stdin/stdout giữa Rust (Transport mới tên FwSimTransport) và script; chạy lại toàn bộ test phiên giao thức và luồng ghi an toàn trên firmware thật.

Tiêu chí tiếp tục: trong 2 giờ, đọc 0x10 qua firmware giả lập ra đúng từng byte trang fixture và checksum 0x02 khớp. Không đạt thì dừng, ghi lý do vào DECISIONS.md (ví dụ ngắt USB và trình xử lý quá dính vào thanh ghi phần cứng). Test này không chạy trong bộ test mặc định vì cần ảnh firmware bản quyền nằm ngoài repo; chạy bằng scripts/fw-in-loop.ps1. M7 chỉ làm sau M8, khi mọi thứ khác đã xong (mục 10).

6.5 Ảnh chụp để người dùng duyệt bằng mắt

Ảnh chuẩn do chính ứng dụng sinh chỉ bắt hồi quy, không chứng minh giao diện đúng. Vì vậy E2E còn xuất bộ ảnh chụp mọi màn hình và trạng thái (không thiết bị, đang đọc, đã đọc 4 layer, chọn phím, từng tab hành động, phím đã sửa, hộp thoại diff, đang ghi, lỗi giữa chừng, FILCO Assist đang chạy, sao lưu/khôi phục; mỗi cái ở sáng và tối) vào docs/screenshots/, nhúng vào STATUS.md. Kèm một bảng tự so với trang "M10SP layer setup" (màu, font, nét phím, legend, khoảng cách, chế độ tối), ghi rõ điểm nào còn khác và vì sao.
